# Medication administration: existing deployments

These are **manual, additive, provider-specific SQL scripts**, not Prisma Migrate history. They add only `MedicationAdministration` and its prescription foreign key to a database that already has the matching `Prescription` table. They do not reconcile other schema differences or backfill administration records. The schemas declare only the primary-key index for this model; the UUID is generated by Prisma Client, not by a database default.

1. Schedule downtime and stop all application writers. Identify the exact database and provider (including PostgreSQL schema or the absolute SQLite file path). Explicitly set `DATABASE_URL`; do not rely on application fallback URLs. Take a consistent backup and **verify that it can be restored** before proceeding. For SQLite, use the SQLite backup API/CLI `.backup` or back up the database and its WAL consistently while stopped; for PostgreSQL, use your approved backup/snapshot and restore procedure.
2. Compare the live schema with the matching Prisma schema and **review the SQL and its effects** with a database administrator. Confirm that `Prescription.id` exists with the expected type and primary key, that `MedicationAdministration` does not already exist, and that the target is the intended database/schema. Stop and investigate if it exists or the schema has drifted; these scripts intentionally fail rather than silently accept an incompatible table. Test the reviewed script and recovery procedure on a restored disposable copy first.
3. From the project root, using the installed Prisma CLI and the explicitly set `DATABASE_URL`, optionally inspect the full diff. This can include unrelated or destructive changes; **do not execute the diff without separate review**:

   ```sh
   # PostgreSQL
   npx prisma migrate diff --from-url "$DATABASE_URL" --to-schema-datamodel prisma/schema.prisma --script
   # SQLite (use an absolute file: URL to avoid relative-path ambiguity)
   npx prisma migrate diff --from-url "$DATABASE_URL" --to-schema-datamodel prisma/schema.sqlite.prisma --script
   ```

4. After backup, test and approval, execute **only the appropriate reviewed script once** against the confirmed target. PostgreSQL's connection URL must select the intended schema (for example, `?schema=public`); SQLite must use the confirmed absolute `file:` URL. Prisma `db execute` does not create migration history.

   ```sh
   # PostgreSQL
   npx prisma db execute --url "$DATABASE_URL" --file prisma/migrations-workflow/medication-administration.postgresql.sql
   # SQLite
   npx prisma db execute --url "$DATABASE_URL" --file prisma/migrations-workflow/medication-administration.sqlite.sql
   ```

5. Check the new table, columns, primary key, default and foreign-key cascade against the selected schema; confirm existing records remain intact. For SQLite, run `PRAGMA foreign_key_check` and ensure foreign keys are enabled on application connections. Record the manual application in your deployment change log; use your normal baseline process if adopting Prisma Migrate later. If anything fails, stop and investigate before retrying or restoring the backup. Generate/deploy the Prisma Client for the matching provider, then restart the application and verify health and the medication workflow.

The root README and deployment guide mention `db push` for initialization; **do not use it to upgrade an existing deployment**. Startup checks can report an incomplete schema but do not apply these scripts automatically.
